# ADR-010: Розподілена транзакція підписки через оркестровану Saga

**Статус:** Прийнято

**Дата:** 2026-06-20

**Автор:** Yurii Levchenko

## Контекст

Завдання HW9: *реалізувати розподілену транзакцію між двома мікросервісами за
допомогою **оркестрованої** Saga*.

Після HW7/HW8 система — це два процеси (моноліт + notifier), що спілкуються
асинхронно через RabbitMQ. ADR-009 зафіксував залишковий **dual-write**: `Subscribe`
робить `INSERT subscription` (`confirmed=false`), **потім** окремо публікує команду
на лист-підтвердження. Краш між цими кроками → підписка висить `pending` без листа,
користувач не може її підтвердити, стан **не re-derivable**.

Домен опирається класичній сазі: ключова дія — **надіслати email, а email незворотний**
(не можна «відкликати» лист). Тому наївне «створити + надіслати з відкатом» не лягає —
відкотити email нічим.

Потрібна **крах-безпечна координація** двох кроків через межу двох сервісів:
(1) створити підписку в БД моноліта, (2) надіслати лист у notifier — з гарантією
узгодженості й видимістю збою для користувача.

## Розглянуті варіанти

### 1. Лишити dual-write без координації (status quo)
- **Плюси:** нуль нового коду.
- **Мінуси:** краш між `INSERT` і publish → pending-підписка без листа, не
  re-derivable; збій невидимий. Це борг ADR-009. Не задовольняє HW9.

### 2. Two-Phase Commit (2PC)
- **Плюси:** сильна узгодженість, атомарний commit між учасниками.
- **Мінуси:** **блокуючий** (координатор тримає локи на час фази prepare); вимагає,
  щоб **усі** учасники підтримували prepare/commit — а SMTP/email і Redis цього не
  вміють; координатор — single point of failure. Не підходить ні домену, ні HW
  (завдання просить саме Saga).

### 3. Хореографічна Saga
- **Плюси:** без центрального координатора; добра для коротких саг (2-3 кроки).
- **Мінуси:** стан саги **розмазаний** по сервісах — важко робити resume/компенсацію
  на рестарті й моніторити весь процес; HW прямо вимагає **оркестровану**. Відкинуто.

### 4. Оркестрована Saga
- **Плюси:** стан саги — **в одному місці** (таблиця `saga`); просте resume/компенсація
  на рестарті; детальний моніторинг; точно лягає у вимогу HW; коректно працює з
  незворотним email (ставимо його **останнім** кроком — останньому компенсація не потрібна).
- **Мінуси:** найбільший приріст коду (orchestrator + saga-store + outbox + relay +
  sweeper); координатор живе всередині моноліта.

## Прийняте рішення

Обрано **оркестровану Saga** для флоу `Subscribe`. Супутні рішення (узгоджені окремо):

- **Оркестратор — модуль у моноліті**, не окремий процес. Лекція дозволяє розміщувати
  роль оркестратора на одному з сервісів; це дає бонус — `T1` і запис стану саги
  виконуються в **одній локальній Postgres-TX**. «Два мікросервіси» = моноліт + notifier.
- **Команди/відповіді — async через RabbitMQ + transactional outbox.** Перевикористовує
  HW8 (ack, дедуп, DLQ), і саме тут outbox прибирає dual-write.
- **Notifier лишається на Redis** — ключ `saga:{id}` для ідемпотентності та статусу
  відправки. Outbox реалізуємо лише на боці моноліта (Postgres).
- **Незворотний крок (email) — останній.**
- **Компенсація = retry email (бюджет спроб), потім позначити підписку `failed`**
  (tombstone, не hard-delete) — щоб збій був видимий на UI.
- **UI:** additive поле `status` у відповіді `GET /subscriptions` + polling на сторінці.
  Шляхи/методи/статус-коди 4 ендпоінтів **не міняються** — лише additive-поле в тілі.

## Форма саги

**Учасники:**

| Учасник | Сховище | Роль / кроки |
|---|---|---|
| Orchestrator (модуль моноліта) | Postgres: `saga`, `outbox` | керує станом, relay (outbox→брокер), resume-sweeper, консюмить reply |
| Subscription (модуль моноліта) | Postgres: `subscriptions` | `T1` create `pending` / `C1` mark `failed` |
| Notifier (окремий процес) | Redis: `saga:{id}` | `T2` send confirmation (ідемпотентно за `saga_id`) + reply |

**Кроки і компенсація:**

| Крок | Локальна дія | Компенсація |
|---|---|---|
| `T1` | `INSERT subscription(pending)` | `C1`: `UPDATE subscription SET status='failed'` |
| `T2` | надіслати лист-підтвердження (idempotent за `saga_id`) | — (останній крок, не компенсується) |

**Потік (happy path) — `T1` в одній транзакції:**

```
POST /subscribe → валідація + GitHub-exists + дубль-чек (синхронно)
        │ ок
        ▼
  ┌─ одна Postgres-TX ───────────────────────────────────────────┐
  │  INSERT subscriptions(pending)                                 │
  │  INSERT saga(state=SUBSCRIPTION_CREATED)                       │
  │  INSERT outbox(routing_key=saga.send_confirmation, payload)    │
  └────────────────────────────────────────────────────────────────┘
        │ 200 "check your email" одразу
        ▼
  relay: SELECT outbox WHERE published_at IS NULL → publish → mark published
        ▼
  notifier: dedup за saga_id → надіслати лист → reply(sent|failed)
        ▼
  orchestrator консюмить reply → COMPLETED
```

**Стан-машина:**

```
SUBSCRIPTION_CREATED ──reply: sent──────────────▶ COMPLETED
        │
        └──reply: failed (після retry-бюджету)──▶ COMPENSATING ──C1──▶ FAILED
```

**Нові таблиці (ескіз колонок):**

- `saga`: `id` · `subscription_id` · `email` · `repo` · `state` · `attempts` · `last_error` · `created_at` · `updated_at`
- `outbox`: `id` · `saga_id` · `routing_key` · `payload (jsonb)` · `created_at` · `published_at (NULL = ще не відправлено)`

## Обробка збоїв (ack + idempotency + resume)

`resume-sweeper` (на старті процесу + періодично) перебирає саги не в
`COMPLETED/FAILED` і пере-проганяє їх.

| Краш де | Самовідновлення |
|---|---|
| після commit `T1`, до публікації | relay знаходить `published_at IS NULL` → публікує |
| після публікації, до reply | RabbitMQ redeliver; notifier дедуп за `saga:{id}` → не дублює лист → reply повторюється |
| reply загубився | sweeper по timeout повторно публікує команду → notifier re-reply |
| SMTP назавжди впав (retry-бюджет вичерпано) | reply `failed` → `COMPENSATING` → `C1` → `FAILED` |
| краш під час компенсації | sweeper повторює `C1` (ідемпотентний `UPDATE`) |

## Наслідки

### Позитивні
- **Узгодженість** між створенням підписки і відправкою листа через крах-безпечну сагу.
- **Закриває dual-write борг ADR-009** транзакційним outbox.
- **Resume на рестарті:** незавершені саги продовжуються або компенсуються — нема
  «застряглих» pending без листа.
- **Збій видимий користувачу** на UI (`status=failed`) — не мовчазна втрата.
- Перевикористовує інфраструктуру HW8 (ack, Redis-дедуп, DLQ).
- Кроки ідемпотентні й семантично коректні (email — термінальний; `C1` — зворотний).

### Негативні
- Найбільший приріст коду/складності в проєкті (orchestrator, saga-store, outbox, relay, sweeper).
- +2 таблиці (`saga`, `outbox`) і міграції.
- Notifier отримує reply-шлях і Redis-стан саги (був майже stateless — лише дедуп).
- `GET /subscriptions` тепер повертає й непідтверджені (`pending`/`failed`) рядки —
  невелике розширення семантики «active subscriptions» (additive поле `status`).
- Оркестратор у моноліті: якщо ментор вимагатиме окремий процес — патерн ідентичний,
  винесемо окремим кроком.
