# ADR-007: Структуроване логування (slog) і конвеєр логів до Elasticsearch

**Статус:** Прийнято

**Дата:** 2026-05-29

**Автор:** Yurii Levchenko

## Контекст

До цього застосунок логував через stdlib `log` у вигляді plain-text рядків у stdout (`log.Printf("Scanner: new release detected for %s: %s", ...)`). Цього достатньо щоб подивитись логи одного контейнера через `docker logs`, але не масштабується:

- **Неможливо шукати за полями.** "Покажи всі помилки за останню годину для репо `golang/go`" — у plain-text це grep по рядку, крихкий і повільний.
- **Неможливо агрегувати.** "Скільки 5xx відповідей за сьогодні", "топ endpoint-ів за латентністю" — над текстом не зробиш.
- **Логи живуть лише поки живий контейнер.** Рестарт app — і попередні логи зникли (для single-instance dev це майже завжди втрата).
- **Немає кореляції запиту.** Не можна простежити "усе, що сталось у межах одного HTTP-запиту".

HW6 вимагає структурованого логування і конвеєра, який передає логи у кластер Elasticsearch для пошуку й агрегації, з візуалізацією в Kibana.

Треба прийняти два пов'язані рішення: **(1)** яким бути логуванню в коді Go, і **(2)** як доставляти логи в Elasticsearch.

## Розглянуті варіанти

### Рішення 1 — бібліотека логування

#### 1a. Залишити stdlib `log` (plain-text)
- **Плюси:** нуль змін.
- **Мінуси:** не структуровано; ES не зможе індексувати поля; не вирішує задачу.

#### 1b. `log/slog` (stdlib, JSON-handler)
- **Плюси:** вбудований у Go 1.21+ — нуль зовнішніх залежностей. JSON-output з коробки. Структуровані key/value поля. Конфігурується один раз на старті (handler + default logger), решта коду викликає `slog.Info(...)` без прокидання логера через конструктори.
- **Мінуси:** трохи повільніший за zap/zerolog на дуже високих обсягах (не критично для нашого масштабу).

#### 1c. `zap` або `zerolog` (сторонні)
- **Плюси:** найшвидші, zero-allocation; багаті можливості.
- **Мінуси:** зовнішня залежність; передчасна оптимізація для навчального single-instance проєкту. Для конвеєра це нічого не дає — Filebeat однаково парсить будь-який JSON зі stdout, незалежно від бібліотеки, що його згенерувала.

### Рішення 2 — спосіб доставки логів у Elasticsearch

#### 2a. App пише напряму в Elasticsearch (ES-output у коді)
- **Плюси:** немає окремого компонента-доставника.
- **Мінуси:** застосунок прив'язується до ES (знає про його адресу, формат, версію); при недоступності ES логіка надсилання логів ускладнює app; порушує розділення відповідальностей — бізнес-сервіс не має знати про сховище логів.

#### 2b. Filebeat (lightweight log shipper від Elastic)
- **Плюси:** app лишається чистим — пише лише JSON у stdout, нічого не знає про ES. Filebeat окремим контейнером читає лог-файли контейнерів, парсить, фільтрує і шле в ES. Легкий (Go-бінарник). Стандарт екосистеми Elastic.
- **Мінуси:** ще один контейнер; конфіг Filebeat треба налаштувати (autodiscover виявився капризним — використали explicit `container` input).

#### 2c. Logstash
- **Плюси:** потужні трансформації, фільтри, багато input/output плагінів.
- **Мінуси:** важкий (JVM, ~1GB RAM); надлишковий для простого "взяти JSON зі stdout → покласти в ES". Filebeat покриває нашу потребу.

## Прийняте рішення

**Рішення 1: обрано `log/slog` з JSON-handler.** Налаштовується один раз у `internal/logging.Setup(level)`, який встановлює handler як default (`slog.SetDefault`). Рівень логування — з env `LOG_LEVEL` (debug/info/warn/error). Решта пакетів викликають `slog.Info/Warn/Error` зі структурованими полями:

```go
slog.Info("new release detected", "repo", repoStr, "tag", latestTag)
slog.Error("scanner failed to get latest release", "repo", repoStr, "err", err)
```

HTTP-запити логуються окремим middleware (`internal/middleware.RequestLogger`): один структурований рядок на запит з полями `method, path, status, duration_ms, client_ip, request_id`. `request_id` генерується (або читається з заголовка `X-Request-ID`) і повертається у відповідь — для кореляції.

**Рішення 2: обрано Filebeat.** Окремий контейнер (у `docker-compose.observability.yml`):
- читає stdout-логи контейнерів (`type: container`, монтує `/var/lib/docker/containers` read-only);
- процесором `decode_json_fields` піднімає slog-поля (`level`, `msg`, `repo`, `request_id`, ...) у корінь документа — стають окремими полями для пошуку;
- процесором `drop_event` лишає лише логи app-контейнера (без шуму postgres/redis/kibana);
- пише в індекс `notifier-logs-*` в Elasticsearch.

Повний конвеєр: **app (slog JSON → stdout) → Filebeat → Elasticsearch → Kibana**.

Обидва компоненти спостережуваності (ES, Kibana, Filebeat) винесені в окремий `docker-compose.observability.yml`, щоб не сповільнювати звичайний dev/test-запуск (unit/integration/e2e з HW5).

## Наслідки

### Позитивні
- **Пошук за полями:** у Kibana `level: "ERROR"`, `status >= 400`, `path: "/api/subscribe"` — миттєво, замість grep.
- **Агрегація:** кількість логів по рівнях у часі, топ endpoint-ів, тощо — через Kibana/ES aggregations.
- **Кореляція запитів:** `request_id` дозволяє знайти всі логи одного HTTP-запиту.
- **App лишається чистим:** бізнес-код нічого не знає про Elasticsearch (Filebeat — окремий компонент). Дотримано розділення відповідальностей.
- **Нуль нових залежностей у Go:** slog — stdlib.
- **RED-сигнали на рівні логів:** access-лог містить rate/errors(status)/duration — доповнює Prometheus-метрики (ADR з метрик — окремо).
- **Збереження між рестартами:** логи живуть у ES, а не зникають з контейнером.

### Негативні
- **Більше інфраструктури:** +3 контейнери (ES, Kibana, Filebeat); ES сам по собі їсть ~1GB RAM. Тому — окремий compose-файл.
- **Eventual consistency логів:** між появою логу і його видимістю в Kibana — секунди (Filebeat batch + ES refresh).
- **Конфіг Filebeat треба підтримувати:** фільтр по імені образу (`yurii-levchenko-app`) прив'язаний до назви; при перейменуванні проєкту треба оновити.
- **Security вимкнено в dev:** `xpack.security.enabled=false` — лише для локального запуску; у проді треба TLS + автентифікація.
- **Дублювання поля:** після `decode_json_fields` сире повідомлення лишається в полі `message`, а розпарсене — у корені (невеликий overhead зберігання).
