# ADR-012: Порядок publish→record на release-шляху (замість outbox)

**Статус:** Прийнято

**Дата:** 2026-08-16

**Автор:** Yurii Levchenko

## Контекст

ADR-009 зафіксував залишковий **dual-write**: «запис у БД + publish у брокер» не атомарні,
бо це дві різні системи без спільної транзакції. ADR-010 закрив цей борг транзакційним
outbox — але **лише для шляху Subscribe**. Шлях сповіщень про релізи лишився незакритим,
і жоден ADR цього явно не відзначив.

Конкретне місце — `Scanner.recordAndNotify` (`internal/releasetracking/scanner.go`):

```
RecordRelease(repo, tag)        // 1. Postgres: last_seen_tag = v2.0
   ╳ краш тут
SendReleaseNotification(...)    // 2. RabbitMQ: publish (не виконалось)
```

Наслідок гірший за звичайну розсинхронізацію: наступний цикл порівнює `latestTag` з уже
просунутим `last_seen_tag`, бачить рівність і вирішує, що нічого нового немає. Реліз
**втрачається назавжди** — не відкладається. Sweeper це не підбирає, бо release-шлях
свідомо не є сагою.

Важлива деталь, яка визначає вибір рішення: `s.notifier` тут — це `BrokerPublisher`, а не
SMTP. Помилка на цьому кроці означає «брокер недоступний», а не «лист відбився». Тому
часткова невдача (один підписник із десяти) практично неможлива — або RabbitMQ доступний
для всіх, або ні для кого. Крім того, `MessageId` уже детермінований і per-subscriber
(`release:{repo}:{tag}:{token}`), тобто **дедуп для повторної публікації вже працює** і
його не треба будувати.

## Розглянуті варіанти

### 1. Лишити як є (status quo)
Незворотна втрата сповіщень при краші у вузькому вікні. Відкинуто — це втрата даних.

### 2. Транзакційний outbox для релізів (як у ADR-010)
В одній транзакції: `RecordRelease` + N рядків в `outbox` (по одному на підписника), далі
relay публікує. Дає **нульове вікно**.

Ціна: `RecordReleaseInTx`, транзакція всередині сканера, N вставок на кожен реліз, ріст
таблиці `outbox` пропорційно кількості підписників, і `releasetracking` починає залежати
від `outbox` (зараз не залежить). Відкинуто як непропорційне: прибирає вікно в мілісекунди
ціною сталого ускладнення домену.

### 3. Зробити release повноцінною сагою
Відкинуто одразу: немає що компенсувати (лист або пішов, або ні — відкату не існує) і немає
багатокрокового процесу. Сага без компенсації — чистий оверхед.

### 4. Змінити порядок: publish→record ✅
Спершу опублікувати всім підписникам, тег просунути **лише якщо всі публікації успішні**.

## Рішення

Обрано **варіант 4**.

Тег просувається виключно як доказ того, що кожне сповіщення дійшло до брокера. Будь-яка
помилка — отримання підписників, публікація, сам `RecordRelease` — лишає тег на місці, і
наступний цикл повторює репозиторій цілком.

Це не робить операцію атомарною. Це **міняє напрямок помилки**: незворотна «втрачена
доставка» перетворюється на зворотний «повторний publish», який consumer уже поглинає
дедупом. Для сповіщень такий обмін правильний — краще двічі, ніж жодного разу.

Краш посеред розсилки теж коректний: розіслали 5 із 10, впали, тег не просунувся →
наступний цикл публікує всім 10 → дедуп глушить перших 5, решта отримують.

## Наслідки

### Позитивні
- Прибирає єдину незворотну втрату даних у системі.
- Гарантія release-шляху змінюється з **at-most-once** на **at-least-once** — та сама, що
  вже діє на шляху Subscribe.
- ~15 рядків, нуль нових концепцій, нуль нових залежностей між пакетами.
- Перевикористовує наявний дедуп замість будувати другий механізм.

### Негативні
- **Вікно лишається**, лише з безпечнішого боку: краш між публікацією і `RecordRelease` дає
  повторну публікацію наступного циклу (глушиться дедупом).
- **Ризик застрягання:** постійна помилка публікації для одного підписника тримала б тег
  нескінченно, повторюючи розсилку всім щоцикла. Приймаємо, бо помилка на цьому рівні —
  недоступність брокера, тобто транзієнтна і спільна для всіх. Якби стало проблемою —
  лічильник спроб на репозиторій із примусовим просуванням і логом permanent failure.
- **Межа дедупу — TTL 24 години.** Застрягання довше доби дасть реальний дубль. Це означало б
  добу лежачого RabbitMQ.

### Коли перейти на варіант 2
Якщо підписників на один репозиторій стануть тисячі: розсилка триватиме хвилини, вікно
зросте пропорційно, і часткові збої стануть реальними. Тоді outbox виправданий.
