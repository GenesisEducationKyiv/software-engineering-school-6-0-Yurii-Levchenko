# ADR-009: Вибір брокера повідомлень — RabbitMQ

**Статус:** Прийнято

**Дата:** 2026-06-20

**Автор:** Yurii Levchenko

## Контекст

У HW7 Notifier винесено в окремий процес. До HW8 моноліт спілкувався з ним
**синхронно по HTTP**: `Scanner`/`Subscribe` робили `POST` і **чекали** відповіді.
Наслідок — якщо notifier лежить, лист губиться, а сам запит підписки падає з
помилкою, хоча для користувача важливе тільки «підписку створено».

Відправка email — це **повільний side-effect, що може впасти** (SMTP недоступний,
таймаут). Користувачу не треба чекати на нього синхронно, а тимчасова недоступність
notifier-а не повинна ні втрачати лист, ні ламати запит. Тобто потрібне **надійне
асинхронне повідомлення** між двома сервісами.

Вимоги до транспорту:

- **Persistence** — повідомлення переживає рестарт брокера/споживача.
- **Ack + redelivery** — повторна доставка, якщо споживач упав до підтвердження
  (гарантія at-least-once).
- **Routing** — різні типи листів (`confirmation` vs `release`) за одним з'єднанням.
- **Dead-letter (DLQ)** — куди відкладати «отруйні» повідомлення, що не обробляються.
- **Self-hosted у docker-compose** — школа ганяє весь стек локально (integration/e2e),
  без хмари.

Лекція L14 (Message bus & broker) і завдання HW8 прямо вимагають справжній брокер.

## Розглянуті варіанти

### 1. Redis Pub/Sub
- **Плюси:** Redis уже є в стеку (кеш GitHub API); найпростіше; низька затримка.
- **Мінуси:** fire-and-forget — **без persistence і без ack**. Якщо notifier лежить у
  момент publish, повідомлення просто зникає → втрачений лист. Не задовольняє вимогу
  гарантованої доставки.

### 2. Redis Streams
- **Плюси:** persistence (в Redis) + ack + consumer groups; Redis уже в стеку — нуль
  нової інфраструктури. (Тіммейт Майкл обрав саме Redis-черги.)
- **Мінуси:** слабкий роутинг (нема exchange/routing keys), **нема нативного DLQ** —
  reliable-чергу довелося б будувати руками (Lua-скрипти, visibility-timeout, reaper).
  І не дає досвіду з канонічним брокером, на якому будується лекція.

### 3. RabbitMQ
- **Плюси:** класична **черга задач** — durable-черги, manual ack (at-least-once),
  гнучкий роутинг через exchange + routing keys, вбудований **dead-letter** (DLX/DLQ),
  management UI. Піднімається одним контейнером. Канонічний «message broker» з лекції L14.
- **Мінуси:** +1 контейнер і ще одна точка відмови; amqp-канал не concurrent-safe
  (потрібен mutex у publisher); складніший в експлуатації, ніж Redis-only.

### 4. Apache Kafka
- **Плюси:** дуже високий throughput, довга persistence з реплеєм, партиціонування,
  кілька незалежних консюмерів одного потоку.
- **Мінуси:** створений для **event streaming** і великих обсягів, а не для черги
  задач; важкий в експлуатації (ZooKeeper/KRaft, тюнінг); надлишковий для нашого
  обсягу (поодинокі листи). Зайва складність без вигоди.

### 5. AWS SQS (+ SNS)
- **Плюси:** керована черга, нуль адміністрування, надійність «з коробки».
- **Мінуси:** хмарний / vendor-locked — **не піднімається локально** в docker-compose,
  на якому школа ганяє весь стек; integration/e2e без AWS не запустяться. Не підходить
  для цього проєкту.

## Прийняте рішення

Обрано **RabbitMQ** (бібліотека `rabbitmq/amqp091-go`).

Це найкращий збіг для надійної **черги задач** із роутингом і DLQ, що піднімається
локально та є канонічним брокером, на який орієнтована лекція. Найближчий конкурент —
**Redis Streams** (уже в стеку), але ми свідомо обрали справжній брокер заради
exchange-роутингу, нативного DLQ і релевантного досвіду. Kafka і SQS відкинуто як
надлишкові / хмарно-залежні для цього масштабу.

## Топологія

| Елемент | Значення |
|---|---|
| Exchange | `notifications` (тип `direct`) |
| Routing keys | `confirmation`, `release` |
| Черга | `notifications` (durable) |
| Dead-letter | `notifications.dlx` (fanout) → `notifications.dlq` |
| Ack | manual (autoAck=false) — підтверджуємо лише **після** відправки email |
| Delivery mode | `Persistent` — повідомлення зберігається на диск брокера |
| Дедуп | детермінований `MessageId` (`confirm:{token}`, `release:{repo}:{tag}:{token}`) → ключ `processed:{id}` у Redis (TTL 24h) |
| Prefetch | `Qos(10)` — максимум 10 непідтверджених повідомлень в обробці |

## Наслідки

### Позитивні
- Підписка успішна навіть коли notifier/SMTP тимчасово лежать — лист чекає в черзі і
  не губиться.
- at-least-once (ack після відправки) + Redis-дедуп (idempotency) = **effectively-once**:
  дублі можливі, але ефект один (один лист).
- DLQ ізолює «отруйні» повідомлення замість нескінченного redelivery.
- Гнучкий роутинг: один exchange обслуговує різні типи листів за routing key.
- Management UI (`:15672`) для дебагу черг і спостереження за ack.
- Інтерфейси `EmailNotifier`/`ReleaseNotifier` не змінились — транспорт пройшов
  SMTP → HTTP → RabbitMQ без правок у `service`/`scanner` (вигода з DIP).

### Негативні
- +1 інфраструктурний контейнер і нова точка відмови (потрібні durable-конфіг і healthcheck).
- amqp-канал не safe для конкурентних publish → publisher тримає `sync.Mutex`.
- Складніша експлуатація, ніж Redis-only-варіант.
- **Dual-write лишається:** «запис у БД + publish у брокер» не атомарні (дві різні
  системи) — краш між кроками розсинхронізує стан. Вирішується transactional outbox
  (див. ADR-010 / HW9).
